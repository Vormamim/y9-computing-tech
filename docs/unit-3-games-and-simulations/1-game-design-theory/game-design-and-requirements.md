# Game Design and Requirements

!!! info "Learning Intention"

    Specify the functional requirements of a game or simulation, including stating the purpose of a system, describing use cases and developing test cases of inputs and expected outputs

    Specify the non-functional requirements of a game or simulation


!!! success "Success Criteria"

    I can distinguish between functional and non-functional requirements of video games.

    I can specify functional and non-functional requirements of a video game in a given scenario.


Before a game is developed, the development team needs to understand what the game is expected to do and what constraints it must operate under. These expectations are called requirements. Requirements provide a clear description of what the client and users need from the finished product. Without clear requirements, different people involved in a project can make different assumptions about what the game should contain.

## Functional Requirements

A functional requirement describes something the game must do. Functional requirements are concerned with features, actions and behaviour.

For example, a game might need to allow a player to:

* Create a profile
* Select a mission
* Customise a vehicle
* Save progress
* Compete against another player

Each of these describes behaviour that the software must provide.

A useful way to identify a functional requirement is to ask:

> What does the system need to do?

## Non-Functional Requirements

A non-functional requirement describes a quality, constraint or condition that the game must satisfy. It is not usually describing a new feature; instead, it describes how the system should operate or a limitation under which it must operate.

A game might need to:

* Load a level within a particular amount of time
* Operate on a specified type of device
* Protect player information
* Remain usable for people with particular accessibility needs
* Maintain an acceptable level of performance

A useful question for identifying a non-functional requirement is:

> How well does it need to work, or what restriction does it need to meet?

## Understanding the Difference

The distinction can sometimes be subtle.

* “Players can change the difficulty level” is functional because it describes something the game allows the player to do.
* “The difficulty setting must be accessible from the main menu” describes a usability requirement.
* “The game saves the player's progress” is functional.
* “The game must save progress without noticeable delay” is non-functional.

## Identifying Requirements in a Client Brief

A client brief often contains requirements without explicitly labelling them. Students therefore need to read the scenario carefully and identify the needs hidden within it.

They should consider:

* Who the users are
* What those users need to accomplish
* Where the game will be used
* What platform it will run on
* What restrictions or expectations the client has

Age, audience, hardware, accessibility, performance, privacy and budget can all influence the design.

## Writing Clear Requirements

Requirements should be specific enough that developers can make decisions about whether they have actually been met.

!!! warning "Make Requirements Clear"

    “The game should be easy to use” is difficult to measure because different people may have different ideas about what “easy” means.


A more useful requirement might specify that a new player should be able to begin a game without assistance after completing a short tutorial.

Clear requirements reduce misunderstandings between the client and development team and give developers something against which the completed system can be evaluated.
